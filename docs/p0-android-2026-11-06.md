## Default startup and window recovery

The final APK now starts correctly on the observed Pixel XL / API 33 arm64
emulator with `-gpu host`, without `WGPU_BACKEND` or `-feature -Vulkan` overrides.
The renderer avoids only the exact known-corrupt SwiftShader Vulkan signature
(LLVM 10.0.0, VirtualGpu, vendor `0x1ae0`, device `0xc0de`), and only after a
surface-free GLES device probe succeeds. Empty/mixed/physical/unknown Vulkan
adapter sets and explicit backend/device overrides preserve their old behavior.
GL limits, texture format and real device creation are checked before switching;
an unsupported GL adapter does not trigger the workaround.

This is a compatibility workaround, not a Vulkan driver fix. The same final APK
still fails the pixel test when explicitly forced to Vulkan, with the selected
Vulkan adapter confirmed in logcat. A temporary experiment keeping Vulkan but
changing storage instance data to texture data also failed; it was removed.
These results do not establish an SSBO root cause.

A separate confirmed lifecycle defect was fixed: NativeActivity acknowledged
window destruction before detaching its surface, and retained the old EGL/Vulkan
connection. The destruction callback now drops the surface before releasing the
NativeWindow and returning the ACK. Device, queue, pipelines and glyph atlas
are retained. Init/resize remain deferred outside that callback's lock boundary.

Rejected configuration stays detached and retries after 250 ms; a termination
cancels pending retries. The native readiness API becomes true only after a
successfully presented frame on the current surface. The renderer distinguishes
a retained renderer from an attached, configured surface.

`ModelPickerRendererTest` passed four same-Activity CREATED → RESUMED cycles on
the final default path. Each cycle checks readiness=false while detached and
true after presentation, an opaque popup interior and retained title glyphs.
The final screenshot was visually inspected. A pure lifecycle test injects a
failed transition and verifies delayed retry and cancellation; actual driver
configuration failure was not injected into the device.

## Manual model and unsent draft acceptance

The opt-in Android test uses real touches, swipes and native keyboard input. On
the final APK's default backend, it entered a previously absent synthetic model
ID/name, saved it through the existing provider editor, selected it, and created
a conversation while preserving the original unsent draft. The native catalog
revision increased and message count stayed zero. It refuses to reuse an
existing model or draft as evidence of a fresh successful edit.

After an external force-stop and confirmation that the old process was gone,
a separate test verifies a new launch instance, the unchanged persisted
generation/digest and writer identity before the UI starts, then the exact
selected model and draft in the actual native editor after hydration. No
credentials, provider discovery or model requests are involved. The test cache
receipt is evidence only; production code never reads it or uses it as storage.

The fixture is an isolated Pixel XL, 1440×2560, 560 dpi, portrait and light mode.
Reproduction commands are in the [Android README](../apps/gpui/README.md#android).
This covers the manual-provider path, not live discovery, account changes or
physical-device acceptance.
